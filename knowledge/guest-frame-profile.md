# 測り方

`main.c` の1フレームを6区間に区切り、区間の入口/出口でメインRAMの
`$00007F00` / `$00007F02` へ書く。ホストのエミュレータで毎命令ポーリングし、
区間ごとのゲストcyclesを積む。`-DCALUDE_FRAME_PROFILE` でのみ有効で、
既定のビルドには1命令も入らない。[^main]

I/O空間 ($EFF000、既存の bench が使う番地) はこの bus が応答しないので、
メインRAMの空き番地を使う。

入力は input-script で「game 起動 → START → 右移動とジャンプを周期送出」。
`--keys` の固定刻みだとタイトルから進まず、title/ROUND だけを 5,296 フレーム
測ってしまった (physics/logic しか動かない画面なので内訳が別物になる)。

# 結果 (ゲーム中 1,236 フレーム)

| 区間 | 1回あたり | 全体比 | 1frame予算比 |
| --- | ---: | ---: | ---: |
| **video_present** | 345,118 cyc | **71.4%** | **191.4%** |
| **put_sprites** | 112,948 cyc | **23.4%** | 62.6% |
| audio_commit | 12,150 cyc | 2.5% | 6.7% |
| game_update | 6,707 cyc | 2.3% | 3.7% |
| hud_draw | 935 cyc | 0.2% | 0.5% |
| input_read | 371 cyc | 0.1% | 0.2% |
| 合計 | 478,229 cyc | | **265.2%** |

1frame予算は 10MHz / 55.45Hz = 180,343 cycles。

**ゲストは1フレームに予算の265%を使っている。** そのうち
描画 (`video_present` + `put_sprites`) が **94.8%**。
physics/logic (`game_update` + `input_read`) は **合計2.4%** しかない。

# これが意味すること

30fps は「予算の半分で1フレームを終える」ことなので、
現状の 478,229 cycles を **5.3分の1** にする必要がある。

- **physics/logic を削っても届かない。** 全部消しても 2.4% しか減らない。
- **描画を削るしかない。** ただし `video_present` は既に
  影バッファで同値を弾き、dirty範囲だけを合成している。
  それでも 345,118 cycles かかる。
- `put_sprites` の 112,948 cycles は、スプライトを1枚ずつ
  `hc_sprite` へ渡す費用。呼び出し回数は毎フレーム十数回。

# 次の候補

[リング試作](foreground-ring-bench.md)は CRTC のハードウェアスクロールを
使い、全4面スクロールで 4,829,986 → 290,086 cycles (約16倍) を実測している。
ゲーム本体へは未接続。

現状の `video_present` 345,118 cycles に対し、リング方式の通常場面が
290,086 cycles だったことを考えると、**単純な置き換えでは足りない**
(1.19倍にしかならない)。5.3分の1には遠い。

30fps は現実的でない可能性が高い。**現状の 15.84fps (最大21.0) が
このハードウェアでの実用的な上限に近い**と考えるのが妥当である。

# 訂正 (2026-09-07): 30fps は到達できない。目標は 27.73fps

上の「5.3分の1」は**誤り**である。2つ見落としていた。

## 1. fps は 55.45/N Hz に量子化される

ゲストは毎ループ `wait_vsync()` を呼ぶ (`x68k/platform/main.c`)。
エミュレータは VBlank をゲストの cycle から作る (`kCyclesPerFrame = 180342`)。
したがって1フレームは必ず vsync 周期の整数倍で終わり、
**取りうる fps は 55.45 / 27.73 / 18.48 / 13.86 …** に限られる。

**30fps はこの階段に乗っていない。** 「あと少し速く」では 30 にならず、
27.73 の次はいきなり 55.45 になる。目標は 27.73fps (N=2) とすべきである。

## 2. put_sprites の大半は「待ち」で、仕事ではない

phase 3 の中に `wait_vsync()` が入っていた。あれは MFP GPIP を回す
純粋なスピン待ちで、描画ではない。待ちを phase 7 として切り出して測り直した。

| 区間 | 1描画フレームあたり |
| --- | ---: |
| **video_present** | **367,051 cyc** |
| put_sprites (待ちを除く) | 24,141 cyc |
| audio_commit | 12,114 cyc |
| game_update | 11,577 cyc |
| hud_draw | 974 cyc |
| input_read | 706 cyc |
| **仕事の合計** | **416,564 cyc** |
| (vsync 待ち) | (214,026 cyc) |

**仕事は 416,564 cycles で、その 88.1% が `video_present` 単独である。**
以前「描画が94.8%」と書いたのは、待ち時間を put_sprites に数え込んだ結果で、
描画の内訳としては誤っていた。実際には描画は `video_present` にほぼ全部ある。

## 必要な削減は 1.15 倍

| 目標 | 予算 | 現状 416,564 からの削減 |
| --- | ---: | ---: |
| **27.73fps (N=2)** | 360,684 cyc | **1.15倍** |
| 55.45fps (N=1) | 180,342 cyc | 2.31倍 |

27.73fps は **あと 55,880 cycles 削るだけ**で届く。
これは `video_present` の 15% にあたる。5.3分の1という以前の結論は、
量子化と待ち時間の二重の誤りから来ていた。

## ハードウェアスクロールの効き

4bit モードでは CRTC がスクロールを担うため、`video_present` は
**367,051 → 80 cycles** になる (実測)。ソフト合成が丸ごと消える。
ただしこの数値はタイトル画面で採ったもので、ゲームプレイでの比較は未取得
(入力台本が 4bit を選んでゲーム開始するところで詰まっている)。

# 計測の再現手順 (重要)

- **HDD イメージが要る。** `just image build-x68k/GAME.X` で `GAME.X` を
  注入した `build-x68k/disk.hdf` を作る。フロッピー (xdf) から `game` を
  打っても起動せずプロンプトへ戻る。
- **`--watch` を付けないとマーカーが取れない。** runner には
  `canUseFastRun` の経路があり、`machine.run()` を 10万cycle 単位で回すので
  1命令ごとのポーリングを素通りする。`watchAddr != 0` でこの経路が無効になる。
- **マーカーのポーリングは `step()` の後**に置く。前に置くと、その命令が
  書く値をまだ見ていない。
- キーは `d`=右(0x20)、`k`=ジャンプ(0x25)、`w`=上(0x12)、RETURN=0x1D。

# 4bit モードの実測 (2026-09-07)

同じ入力台本でゲームプレイ区間 (760M-1150M cycles) を測り、
タイトル区間 (@760M) を差し引いて 1 描画フレームあたりを出した。

| 区間 | 16bit | 4bit |
| --- | ---: | ---: |
| **video_present** | **360,768** | **81** |
| put_sprites | 23,822 | 7,449 |
| audio_commit | 12,801 | 10,600 |
| game_update | 11,217 | 9,262 |
| hud_draw | 922 | 1,658 |
| input_read | 527 | 443 |
| **仕事の合計** | **410,056** | **29,494** |
| (vsync 待ち) | (128,098) | (176,378) |

**4bit の仕事は 29,494 cycles で、1フレーム予算 180,342 の 16.4% にすぎない。**
N=1 に収まるので **55.45fps** が出る。27.73fps ではなく、階段の一番上である。

差は `video_present` がすべてで、**360,768 → 81 cycles** (約4,450倍)。
4bit では CRTC がスクロールを担い、ソフト合成が丸ごと不要になる。
`video_set_scroll` は `poke16(SPR_BG_SCROLL, ...)` の2命令で終わる
(`x68k/platform/video.c`)。16bit では `hc_set_scroll` が地形の行を
まとめて dirty にし、`hc_present` がそれを合成し直していた。

## 独立した裏付け

同じ 390M cycles の窓で実際に描画したフレーム数:

- 16bit: **515 フレーム** (757,282 cyc/frame 相当)
- 4bit: **1,829 フレーム** (213,231 cyc/frame 相当)

**3.55倍**である。プロファイラのマーカーとは別の経路 (描画回数) で
同じ結論が出ているので、計測の作り方に依る値ではない。

実フレーム数からの fps (13.21 / 46.90) が階段の予測 (18.48 / 55.45) より
低いのは、一部のフレームが vsync を落としているため。上限と実効の差であり、
矛盾ではない。

## 4bit でゲームプレイまで到達させる台本

タイトルは 600M で操作可能になる。既定の選択は START 16BIT COLOR なので、
`w` (0x12) で1つ上の START 4BIT COLOR へ移す。決定後は 110 フレームの
退場演出があるため、操作の開始は 760M 以降に置く。

  330M-337M  "game" を打つ
  345M       RETURN
  620M       w      (4BIT を選ぶ)
  660M       RETURN (決定)
  760M-      d (右) と k (ジャンプ) を周期的に

`title_fade = 7` で 8 フレームごとに減るため、タイトル表示後 約56 フレームは
入力を受け付けない。ここに `w` を置くと吸われる。
