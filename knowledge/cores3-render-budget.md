# 条件

CoreS3、音源ON、音量40/255、同じflash HDDのGAME.X。USB接続で再起動後20秒待ち、`Jgame\r`を送信。60秒のログを取得後、LCDフレームを採取した。JIT切り替えはCore1で`JIT applied: ON`となり、`event_driven=1 jit_active=1 probe=0`を確認した。

各版1回の探索的な測定であり、同一ゲストサイクルで揃えた比較や60秒×3回の統計ではない。ゲーム内時間の進み方が違うため、同じ実時間窓でも曲の相が違う。倍率や全編の改善率を断定しない。

# JITのみ

アプリSHA256 `eb63245ca9729ef7ed4976527b61e01b244c468773c484c9850ebf751e751285`（前回適用版）。約36〜61秒の5秒窓で813〜866kHz、後半536〜684kHz。音声は一部区間で17〜22 blocks/sとなり、30.5176 blocks/sに不足。旧30Hz開始間隔のままではJIT有効化だけで解消しなかった。

LCD画像`build-x68k/cores3-jit-title.png`を目視し、タイトルイラストとSTART/CONTINUE/OPTIONを確認した。

# 描画時間予算を追加

`render_budget.h`にESP32非依存の制御を追加。次の描画開始時刻を以下とする。

`max(開始時刻 + 100000µs, 終了時刻 + ceil(実測描画時間 × 1.5))`

最大10fps、描画終了後に実測時間の1.5倍を他の処理へ残す。休止中に予算を貯めない保守的な制御で、遅れたフレームを後追い描画しない。ゲストのrun、VBlank、割り込み、ゲーム更新は間引かない。描画時間と合成成功回数を常設ログにした。これは設計の初期10fps候補であり、最終表示品質ではない。公開枠の事前取得、局所再合成、15/20/30fps比較は未実装・未実施。[^design]

- アプリ608400 bytesを0x10000へ書き込み、hash検証成功。ROM/HDDは変更していない。
- bin SHA256 `399dcbed378b0ae0c80da7eef7786520e73b367faf33bc35f6ca180369169eaa`、実機ELF SHA先頭`e55a4bb3a`。
- 約36秒の窓: 描画1,788,991µs/45回/5003ms（約35.8%）、実効1847kHz。約41秒の窓も1808kHz。
- 後半は描画約1.6〜1.8秒/5秒、41〜44回を維持していても536〜905kHzに低下し、音声16〜20 blocks/sの区間が残った。
- 約56秒の窓ではrun 512,021µsと描画1,707,399µsの合計が約2.22秒で、実測窓5.035秒との差が約2.82秒ある。音声合成は候補だが、未計測なので原因の確定とはしない。
- 起動後約81秒までの取得ログにwatchdog警告なし。LCD画像`build-x68k/cores3-budget-title.png`でタイトルとメニューを目視確認。撮影はLCDへ渡したRGB565の取得とPNG変換で、画像の描き替えではない。

# 検証と次の作業

`just test-host`成功（CTest 2/2、32.90秒）。描画間隔、重い描画の後の実測時間比例の待ち、長時間休止後に連発しないことを新規テストした。`just test-san`も2/2成功（41.58秒、macOSではUBSan）。実機ビルド、`git diff --check`、`just --fmt --check`成功。変更後の統合`just check`は未実行。

当時の次手はCore1の音声合成µs・ブロック数・最大時間の直接計測だった。下記追記で実施済み。音声の周波数計算は既にレジスタ更新時にキャッシュされており、`pow()`を毎サンプル呼んでいるという推測で既存最適化を繰り返さない。速度不足・音声供給不足・滑らかな表示・全編実機検証は依然未完了。再起動するとJITは既定OFFへ戻る。[^implementation]

# 追記: 音声合成時間の実測

Core1の`pumpAudio()`前後をesp_timerで測り、累計µs・成功ブロック数・最大µsを他の計測と同じ5秒窓で報告するよう追加した。純粋な命令実行時間ではなく、割り込み・プリエンプションを含む呼び出しの経過時間。合成方式、ゲーム、音量40/255は変更していない。

608656 bytesの計測追加版を0x10000へ書き込み、hash照合成功。bin SHA256は`bf566761b0fd1dbe5eec5af325164c8d783d7a8cbdeac6f9afe1bd0124856d25`。実機はこの版に更新済み。前回と同じ`Jgame\r`、起動待ち20秒・観測60秒。`event_driven=1 jit_active=1 probe=0`を確認し、LCDフレーム`/private/tmp/cores3-synth-profile.ppm`を取得した。

| 実機の報告時刻 | 窓 | 音声合成 | ブロック数 | 最大/ブロック | 描画 | CPU run |
|---|---:|---:|---:|---:|---:|---:|
| 約36秒 | 5005ms | 1387746µs | 152 | 11405µs | 1829527µs | 1691927µs |
| 約51秒 | 5030ms | 2503391µs | 95 | 32627µs | 1747977µs | 738166µs |
| 約56秒 | 5023ms | 2786108µs | 88 | 32257µs | 1707761µs | 503119µs |
| 約71秒 | 5060ms | 2812881µs | 96 | 32239µs | 1668314µs | 547337µs |

約56秒の窓は音声合成55.5%、描画34.0%、CPU run10.0%。以前の未計測時間の大半が音声合成呼び出しだった。必要出力512/15625秒=32.768msに対し、最重区間は合成自体が約32ms/ブロックを占め、CPUと描画も同じCore1で回す現状では連続供給が間に合わない。起動直後の無音では153ブロックの合成が約0.9ms/5秒で、曲による負荷差が非常に大きい。

これはOPM/ADPCM内部のどの関数が律速かを確定する計測ではない。次の最適化は音源内の反復処理を対象に、旧出力とのサンプル一致と実機時間の両方で評価する。EGの毎サンプルのレート換算やテーブル取得は調査候補であり、効果未検証。単なるチャンネル削減、音量低下、サンプルレート低下はこの結果から正当化しない。

検証: 実機ビルド、書き込みhash照合、約81秒までのUSBログ、LCDフレーム全行取得、`git diff --check`、`just --fmt --check`成功。取得ログにwatchdog警告なし。音源アルゴリズムとホスト対象を変えていないため、この計測追加だけでホストテストは再実行していない。音質・全編プレイ・長時間安定性は未検証。

# 追記: EG事前計算の試作とUSB無応答（復旧未完了）

EGの毎サンプルの64bit乗算を、サンプルレート変更時に計算する4個のu32へ置き換えた。全64レートの表を持たず、内部RAMの増分を12 bytesに抑える候補。`((uint64_t(4+i)<<4)*scale)>>16`の最大値は7340031であり、u32へ先に格納してからレート依存シフトをしても旧式の丸めは変わらない。

`opm_envelope.h`と`test_opm.cpp`に、境界10値と決定的疑似乱数4096値×全63実効レート（258678組）の旧式との一致検証を追加した。候補を本体へ接続した状態で`just test-host` 2/2（35.00秒）、`just test-san` 2/2（42.60秒、macOS UBSan）成功。これは整数式の一致と既存音源テストであり、曲全体の旧PCMとの比較ではない。

候補608720 bytes、SHA256 `a8e2b9f6935019d621c566f785fc6d7aecb92d6d38877a8dd2bb3edc51c52b8e`をアプリ領域0x10000へ書き込み、hash照合には成功した。ROM/HDDは未変更、音量40/255も維持。ところが同条件のUSB取得では、起動ログが`boot: Disabling RNG early entropy source...`（約135ms）で止まり、アプリのログもLCDフレームも取得できなかった。一度再接続しても無応答だったため、取得プロセスを中断した。計測値がないので高速化の効果も、最適化が無応答の原因かどうかも未確定。

本体の`opm.cpp`/`opm.h`は今回の変更だけを戻し、事前計算ヘルパーと等価性テストは未採用候補として残した。再ビルドした復旧用アプリ608656 bytesのSHA256は、直前の動作確認済み`bf566761b0fd1dbe5eec5af325164c8d783d7a8cbdeac6f9afe1bd0124856d25`と一致。しかし復旧書き込みは接続段階で`Failed to connect to ESP32-S3: No serial data received`となり失敗した。**実機にはまだ候補版が残っており、旧版へ復旧済みではない。** ポート`/dev/cu.usbmodem2101`は存在、`lsof`では占有プロセスなし。

次に実機の物理リセットまたは電源再投入で接続を回復し、旧版をアプリ領域だけへ復旧・起動確認する。接続不能のまま書き込みを繰り返さない。今回の候補を採用済み・音声改善済みと扱わない。[^implementation]

# 追記: 最適化前PCMを固定した回帰テスト

実機の物理リセット待ちの間に、`test_opm.cpp`へPCM回帰テストを追加した。基準は`e4356d6f41aadc6a2663be23fcb229397e73ce1e`と差分のない`opm.cpp`/`opm.h`。期待値を仮に0にした採取実行の5件の不一致から、旧音源の出力ハッシュを取得して固定した。候補に合わせて基準値を変更したものではない。

- 条件: 入力レート0（既定値へのフォールバック）/15625/31250/44100/55930Hz。各8192サンプル、合計40960サンプル。
- 8chで全8アルゴリズムと異なるフィードバック・音程・DT1/DT2・MUL・KS・EGレートを使い、2048サンプル後に全chキーオフ、4096で再キーオン、6144で22050Hzへ変更。全条件で非ゼロサンプルが1024個を超えることも検証する。
- 出力をu32へ変換し下位バイトから4 bytesのFNV-1a 64bitハッシュへ投入する。期待値はレート順に`5791532205415170417`, `5791532205415170417`, `15667092462324130126`, `11433102273017827615`, `3975217357743097295`。
- 一時的にEG事前計算をホスト本体へ接続して`just test-host`を実行し、PCMハッシュを含めCTest 2/2成功（34.13秒）。実機ビルド・書き込みは実施していない。その後、本体のOPM変更だけを戻し、最終ソースは旧音源のまま。回帰テストと未採用ヘルパーは残した。

これは指定した刺激に対する旧エミュレータとのハッシュ一致であり、実YM2151への忠実度、曲全体の音質、実機での速度を保証しない。復旧用binは前回と同じSHA256を維持している。USBポートの存在と非占有は再確認したが、物理リセットの連絡がないため再書き込みは保留した。実機に候補版が残る状態は未解消。[^implementation]

最終状態（旧OPM本体＋新規回帰テスト）の`just test-san`もCTest 2/2成功（41.89秒、macOS UBSan）。`git diff --check`成功。通常テストの外部m68kベクタとIPL-ROM指定テストには資料未配置によるスキップがあり、全CPU適合性を検証済みとはしない。

# 追記: 確認済み版への復旧完了

ユーザーのUSB再接続後、`/dev/cu.usbmodem2101`とUSB JTAG/serial debug unitが再出現。確認済み608656 bytesのアプリ（SHA256 `bf566761b0fd1dbe5eec5af325164c8d783d7a8cbdeac6f9afe1bd0124856d25`）を0x10000へ書き込み、hash照合成功。**上記の「候補版が実機に残る」「復旧未完了」はこの追記時点で解消済み。** ROM/HDDは未変更。

最初のログ取得は`DOWNLOAD(USB/UART0)`待機。USB用RTSリセットでも同じモードに戻った。固定版esptool 4.9の`ESP32S3ROM.hard_reset()`が強制download状態を解除する実装であることをローカルソースで確認し、同一ポートから呼ぶ候補も試したが、ROM同期時に無応答となり実行には至らなかった。これらの未成功オプションは取得スクリプトとjustfileから取り除き、依存追加も取り消した。GPIO0や強制download状態が原因だったとは確定していない。

ユーザーの追加操作後、従来の取得手順で`SPI_FAST_FLASH_BOOT`、PSRAM検査成功、アプリELF SHA先頭`25efb701e`、エミュレータ・スピーカー初期化、`JIT applied: ON`を確認。起動待ち20秒＋`Jgame\r`＋観測60秒でタイトル取得成功。`build-x68k/cores3-restored-title.png`を目視し、イラスト・START/CONTINUE/OPTIONを確認した。これはLCDに渡したフレームの取得で、カメラ撮影ではない。

音量40/255を維持。約81秒までwatchdog警告なし。非ゼロPCMは生成されるが、後半は16〜20 blocks/sの区間が再現。約56秒窓は音声合成2785967µs/5023ms、最大32260µs/ブロック、CPU実効525kHzであり、従来の供給不足は残る。復旧は確認できたが、音質・速度改善・長時間安定性・全編実機プレイは完了していない。次は、この復旧版を基準に最適化候補の実機評価を再開する。[^implementation]

# 追記: OPM波形テーブルの初期化ガード除去

実機オブジェクトの逆アセンブルで、`operatorOutput()`の入口が毎回初期化ガードを呼ぶ経路になっていることを確認した。関数内staticの不変`Tables`を名前空間内の`const Tables kTables`へ移し、アプリ起動前に一度だけ同じ計算式で初期化する。変更後はOPMオブジェクトの未定義シンボルから`__cxa_guard_acquire/release`が消え、`operatorOutput`の独立したtext sectionもなくなりインライン化された。同期を無効にするコンパイラ設定や非同期の独自初期化フラグは導入していない。EG事前計算は今回接続していない。

`just test-host` 2/2（33.78秒）、`just test-san` 2/2（44.06秒、macOS UBSan）、`just fmt-check`、実機ビルド、`git diff --check`成功。既存5条件40960サンプルのPCMハッシュ一致を維持。起動時初期化なので、ホストのmain以前の初期化も両ビルドで通過した。

610288 bytes、SHA256 `e3d69337c25d7b8db7980eda27b133d76822d935b04452810164ebf89a8ff7cd`を0x10000へ書き込み、hash照合成功。実機ELF SHA先頭`e67907db3`。ROM/HDD・音量40/255・最大10fps描画予算は維持。起動20秒後`Jgame\r`、観測60秒の同条件で、正常起動・音源ON・`event_driven=1 jit_active=1 probe=0`、約81秒までwatchdog警告なし。現在の実機はこのガード除去版。

変更後の音声合成最大は観測中3717µs。タイトル曲中は主に31 blocks/1016msまたは32 blocks/1049ms（約30.5 blocks/s）を維持し、以前の持続的な16〜20 blocks/sへの落ち込みはこの試行では再現しなかった。実効CPUは曲中の5秒窓で約2050〜2929kHz。ただし各版1回の実時間窓であり、ゲスト時間が速く進むため同一曲相の比較ではない。「全編5倍」「あらゆる音切れ解消」とは結論しない。ゲーム起動直後の無音窓には27 blocks/1016msもあり、リング満杯以外のアンダーランを直接数える計測もまだない。

`build-x68k/cores3-opm-guard-title.png`を取得・目視し、タイトル画面とメニューを確認。物理音質・全ステージ・長時間安定性は未検証。次は実プレイと長時間の供給計測、再生側のアンダーラン計測を行い、残るCPU/描画時間を改善する。今回の変更は音声の主要負荷を減らしたが、要求された全ての供給不足解消と処理速度改善の完了を証明するものではない。[^implementation]
