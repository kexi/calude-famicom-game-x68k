# 前提の訂正

このリポジトリの計測で「ゲーム中のCPU実効は5.0MHz」と記録したが、
**エミュレータ自体は既に実機比100.6% (10063 kHz) に到達している**。
[イベント駆動デバイスとJIT](../../x68k-stackchan/docs/knowledge/event-driven-implementation.md)
に 6970→7495→7620→8844→9060→…→10063 kHz の実測がある。[^emu-knowledge]

差は**何を走らせているか**である。10063 kHz は Human68k のプロンプトで、
5.0 MHz はゲーム実行中。同じ実機・同じファームでも、命令の内訳が違えば
JIT の効き方が変わる。「5.0MHzが上限」という前提で最適化を探すのは誤り。

# 測り方

ホストのエミュレータでゲームを900Mサイクル実行し、**1命令ごとに
`BlockPlanner::planOne` を呼んで JIT が受け付けるかを判定**、
弾かれた命令を実行回数で数えた。静的な命令数ではホットパスは分からない。

`--stats` を付けて `machine.run()` の速い経路ではなく `step()` 経路を通す
(速い経路では1命令ずつ観測できない)。

# 結果

    実行 80,808,040 命令
    JIT可 68,663,910 (85.0%)
    JIT不可 12,144,130 (15.0%)

弾かれた命令を種類別に集計する (上位30命令で不可分の82.7%)。

# 最も費用対効果が高いのは Dn 対象の ANDI/ADDI

`planImmediate` (block_planner.cpp:683) は **CMPI と BTST しか通していない**。
理由はコメントに「ORI/ANDI/SUBI/ADDI/EORI は書き戻しがあるので入れない」
とある。[^planner]

しかし**書き戻し先が Dn なら、メモリの読みガードは要らない**。
CMPI と BTST が既に `mode != 0` を弾いて Dn 限定で通っているのと同じ条件で、
ANDI/ADDI も通せるはずである。

実行回数で見ると、Dn 対象の ANDI/ADDI だけで:

| opcode | 命令 | 実行回数 | 全体比 |
| --- | --- | ---: | ---: |
| 0x0280 | ANDI.L #imm,D0 | 929,886 | 1.15% |
| 0x0240 | ANDI.W #imm,D0 | 468,619 | 0.58% |
| 0x0281 | ANDI.L #imm,D1 | 460,900 | 0.57% |
| 0x0247 | ANDI.W #imm,D7 | 460,844 | 0.57% |
| 0x0640 | ADDI.W #imm,D0 | 460,831 | 0.57% |
| 0x0681 | ADDI.L #imm,D1 | 281,224 | 0.35% |
| | **合計** | **3,062,304** | **3.79%** |

JIT不可 15.0% のうち **3.79ポイント**、つまり**約4分の1**がこれで消える。

# 実装して実機で測った結果: 被覆は上がったが速度は落ちた (2026-09-07)

上の分析にもとづき2件を実装した。どちらもエミッタ側は既に対応済みで、
planner が弾いていただけだった。

| 変更 | 被覆 | 不可 |
| --- | ---: | ---: |
| (変更前) | 85.0% | 15.0% |
| 即値ALUのDn宛て (ANDI/SUBI/ADDI) | 89.2% | 10.8% |
| ADDA/SUBA/CMPA の即値形 | 90.6% | 9.4% |

**実機で測ると遅くなった。**

| 指標 | 拡張前 | 拡張後 |
| --- | ---: | ---: |
| CPU実効 | 4,987 kHz | **4,601 kHz** |
| 音声不足 | 50.1% | 54.0% |
| fps | 7.77 | 7.73 |

2回測って 4,601 と 4,620 kHz。誤差ではなく再現する。

## 原因: arena が満杯で、被覆を広げるとむしろ悪化する

実機の `[jit-runtime]` を見ると、

    blocks=67,291,085  insns=137,239,578
    unsupported=114,664,638  full=107,663,755

**ブロック入口の失敗のうち48.4%が「JITコード領域が満杯」**である。
1ブロックあたり命令数は 2.04。

被覆を広げると1ブロックが長くなり、生成コードも大きくなる。arena は
バンプアロケータで個別ブロックを解放できないので、大きいブロックが入ると
**arena に入る本数が減る**。翻訳できる命令が増えても、置き場が無ければ
その命令は結局インタプリタへ落ちる。差し引きで遅くなった。

これは [cores3-jit-capacity-probe.md](cores3-jit-capacity-probe.md) の
「コード20KiB化でスロットが縮退し 2.72→2.09MHz に悪化」と同じ構造である。
容量が律速のときに被覆を増やすと逆効果になる。

## 教訓

**被覆率は速度の代理指標にならない。** 今回は事前にそう書いておきながら、
実際に測るまで「4.2ポイント増えたのだから速くなるはず」と考えていた。
測って初めて逆だと分かった。

次に手を入れるなら被覆ではなく **arena の容量と追い出し方針**である。
ただし過去に容量を増やして悪化した実測があるので、
「増やせば速くなる」も同じく検証が要る。

変更自体は正しい (861 test cases 全通過、独立モデルとも一致)。
被覆を広げること自体に害はなく、arena が広がれば効くようになる。
そのため revert はしていないが、**この2件だけでは速度は改善しない**。
