# 採用する方針

音声のメモリ所有権と処理上限を先に確定し、同一条件で既存の高速実行経路を評価する。その後、描画の局所再合成でCPU時間を空け、音源をゲストサイクルに同期する。音量はユーザー指定の **40/255** を維持する。

Machine、CPU、VRAM、OPM、ADPCMの所有者はCore1のままとする。Core0は完成済み画素とPCMだけを受け取り、入力・モード切り替え要求をCore1へ送る。Core0から同じMachineを触る並列化は採用しない。

これは実装前の設計であり、ファームウェアの変更・書き込み・実機再起動は行っていない。`verified`はソース監査の記録であり、下記の性能目標や音質の達成を表さない。

# 1. 計測を比較可能にする

ベースラインは実機系統と未コミット差分を特定したものとし、変更前後でGAME.X、ROM/HDD、依存lock、SDK設定、最適化フラグ、CPU周波数、PSRAM設定、画面倍率、入力列を揃える。メタデータに各ハッシュ、実行モード、音声モードを残す。単なる作業ツリーのHEADだけをファーム識別子にしない。

計測はウォームアップ後60秒を最低3回、タイトル、ラウンド、移動・スクロール、敵が多い場面、ボス、ポーズで行う。起動・ロード・JIT初回コンパイルの時間は別に記録する。LCDの大量シリアルダンプは計測窓の外で取得する。同じ入力列の比較にはゲストサイクル基準を使い、操作遅延の評価には別途実時間基準を使う。

1イベント1行のJSONで共通の`run_id`と実測`elapsed_us`を出す。以下を基本項目とする。

| 系統 | 必須指標 |
|---|---|
| 実行 | 要求サイクルと実消費サイクル、ゲストVBlank数、ゲーム更新数、run時間、event-driven/JIT実際の有効状態、フォールバック数 |
| 描画 | 合成回数・合成µs・p50/p95/max、面別時間、再合成tile数、公開成功/失敗、LCD転送時間、実表示fps、最新ゲスト状態からの表示遅延 |
| 音声 | 生成/送信/消費済みサンプル、各キューの最小/最大充填、underflow回数と無音補完サンプル、overflow/破棄、合成µs、送信待機µs、音源イベント遅延、clip数 |
| 実機 | 両コアの稼働/idle時間、最長連続実行、watchdog、内部SRAM/PSRAMのfree・largest、計測器自身の時間 |

`Machine::run()`の戻り値など実際に進んだサイクルを集計する。現状の`totalCycles += sliceCycles`は要求値なので、境界超過・停止を含めると厳密な実効速度ではない。STOPによるゲスト時間進行と実行命令数も別指標にする。

音声の内側`while(pop())`が長時間抜けないと、ログの1秒窓は実際には長くなる。既存の「559ブロック/秒」は約18秒区間の総数という記録で、rateではない。修正後は`blocks_delta * 1e6 / elapsed_us`で計算する。15625Hz・512 samples/blockの定常必要量は **30.5176 blocks/s**。`playRaw`送信数はDAC再生済みサンプル数ではないため、後者を直接取得できない場合は推定値と明記する。

まず通常の毎命令実行、event-driven、event-driven+JITを同一設定で比較する。速度に加えてゲスト時刻で揃えた画面・状態・音源イベント列を比較し、意味を変える高速化は採用しない。モード要求はatomic/command queueでCore1へ渡し、スライス境界で適用して結果を返す。

# 2. 描画と実行の時間予算

Core1の定常必要時間は次式で評価する。各係数は同じモード・同じゲーム場面で測る。

```text
Ucore1 = Fguest × cost_cpu_per_guest_cycle
       + Flcd × cost_compose_per_frame
       + Faudio × cost_synth_per_sample
       + Uinput + Ustorage + Uscheduler + Umetrics

Ucore1 <= 0.85 を設計上の目標とする（残り15%は変動・idle余裕）。
```

10MHzは`Fguest=10,000,000 cycles/s`の最終目標であって、フレーム間引きだけで達成するとは限らない。例えば平均43.3msの合成を30回/秒行うと合成だけで約130%を要する。10回/秒でも約43%。さらに純CPU経路が同一負荷で10MHz未満なら、描画をゼロにしても実時間には届かない。

初期実装はLCDを10/15/20/30fpsで比較し、移動の見え方と実効速度を測る。固定の開始間隔に加え、描画に使った実時間のtoken budgetを設け、余裕がないときは最新状態の描画へ集約する。ゲストのVBlank、割り込み、ゲーム更新、音源イベントは表示フレーム省略によって省略しない。

表示チャンネルに公開可能枠がない場合は、高価な合成へ入る前に検出する。`acquireWritable()`→合成→`publish()`を明示し、Core0のDMA終了後にだけ`release()`される。Core0の転送中バッファを描画先に再利用しない。現行の`waitDMA()`とバイト変換経由の内部DMAバッファ利用は、別途検証なしに取り除かない。[^capture-tree]

## 世代付き局所再合成

フレーム全体のdirtyフラグ追加は既存成果と重なる。新規部分は「どの画素領域を再合成するか」と「二枚の出力バッファがどの世代か」の管理に置く。

320×240出力を16×16の300 tileに分け、Core1に`scene_tile_generation[300]`、各RGB565バッファに`buffer_tile_generation[300]`と`mode_epoch`を持つ。初期化時は全tileを無効とする。描画先ごとに世代が異なるtileだけ、その領域の全レイヤーを正しい優先順位・透明規則で再合成する。tile世代3組を32bitで持つ場合は約3.6KB。

二重バッファでは「前回変化したtile」だけを描いてはいけない。描画先は2回前の内容を持つ場合があるため、各バッファ固有の世代差で判定する。公開失敗でも描画済みバッファの世代は正しいまま保持し、次回の差分に使える。表示済み世代・公開済み世代・合成済み世代を一つのdirty消去で兼用しない。

| 変更元 | 初期の無効化範囲 |
|---|---|
| T-VRAM | 書き換えbyteが表す8画素をviewport/zoomへ写した領域。全planeを考慮 |
| G-VRAM | 実際の`writeGvramDot`による物理画素変更から、表示中page・色モードを考慮した領域 |
| スプライト位置・属性 | 変更前と変更後の外接矩形の両方。消去、反転、優先順位変更を含む |
| PCGパターン | パターンを参照する表示中BGセル/スプライト。初期は該当面全体でも正しさを優先 |
| BGネームテーブル | 対応セルの表示領域。スクロールによるラップを含む |
| パレット | 初期は該当面が重なる全領域。色別使用tile追跡は効果を測ってから |
| 画面モード・面優先順位・表示許可・viewport・zoom | `mode_epoch`更新で全面 |
| BG/画面スクロール | 初期は対象面の全面。安定後にスクロール差分キャッシュを検討 |

書き込み入口にはbyte/word、DMA、IOのread-modify-write、JITの高速メモリ経路、reset/restoreを含める。最終値が同一なら無効化を抑えられるが、その判定用PSRAM readを増やしてCPU経路を遅くしないか測る。追跡できないモードは既存の全面描画へフォールバックする。

描画途中にゲスト実行を挟んで同じMachineから続きを読むと、一枚に異なるゲスト時刻が混ざる。初期版は一回の描画中にゲスト状態を進めず、OSへのyieldだけを許す。実測で音声蓄積時間を超える描画停止が残るなら、入力状態の不変snapshotを作る方式を別段階で設計・評価する。単に数行ずつ描いてその間ゲストを実行する方式は採用しない。

## PSRAMアクセスの削減

既存の8画素テキスト展開・BG上位計算の集約は残す。追加候補は内部SRAMの行/小tile作業領域に必要なVRAMとパレットをまとめて読み、全レイヤーを局所合成してRGB565を連続書き込みする方式。面ごとにPSRAMの出力画像を往復する回数を減らす。

キャッシュは色indexと透明情報を保持するPCGパターン単位から検討し、パレット変更で全パターンの再展開が起きない構造にする。容量上限・hit率・展開費用・内部SRAM残量を必ず測る。全面画像を何枚も追加する案は、コピー費とPSRAM帯域が見合うと確認できた場合に限定する。

既存の「BGセル参照だけをキャッシュ」「HUDのあるゲームでtextなし条件の合成を省略」は効果がなかった。再試行するなら過去と異なる負荷・範囲を説明する。ゲーム領域256×240への限定は、CRTCの表示領域を正しく解釈するか、明示したゲームprofileに限る。他ソフトを無条件に切り取らない。[^runtime-history]

# 3. 音声の参照寿命と実行上限

現行`AudioChannel::pop()`はポインタを返す時点で`readIndex`を進め、そのslotを生産側へ解放する。一方`M5SpeakerSink::write()`は`playRaw()`へ同じポインタを渡し、M5Unifiedはコピーせずcurrent/nextの最大2枚を保持する。リング段数4という距離だけでは、非同期消費中の上書きを禁止できない。現状の`AudioSink`契約「次のwriteまで有効」もM5の参照期間より弱い。これを音質原因の確定とはせず、コードで確認できる寿命リスクとして先に解消する。[^capture-tree][^speaker-source]

## キューの契約

`AudioChannel`を`acquireRead()`/`releaseRead()`方式にし、読み手がPCMをコピーし終わるまで生産側へ解放しない。生産は`acquireWrite()`/`commitWrite()`で、各slotを次の状態として扱う。

```text
FREE → WRITING → READY → READING → FREE
                          ↓ コピー
                   sink専用PCM slot → M5参照中 → FREE
```

リングをそのままM5へ貸し出す設計は初期版では避ける。sinkに固定長PCM slotを3枚持ち、空きslotへ1KBコピーした後にringのread leaseを解放する。15625Hz・16bit monoでコピーする量は約31.25KB/sであり、PSRAM画像帯域に比べ小さい。性能判断は測定するが、曖昧な寿命をリング段数で隠す理由にはしない。

M5専用adapterはchannel 0を単独所有し、repeat=1、stop_current=falseに固定する。current/nextを保持する既存実装では、3枚目の`playRaw`が正常に受理された時点で、最古の1枚は参照対象から外れる。したがってslot nを埋める前に空きであることを確認し、送信nの受理後にslot n-2を再利用可能にする。これはリング消費数とは別にsinkの送信順序で管理する。[^speaker-source]

このadapterは固定したM5版の`_set_next_wav`とcurrent/next切り替えに依存する。実装時は依存lock/hashを記録し、単一送信者・2枚保持・FIFO順序・正常稼働の条件をテストする。APIの戻りtrueだけでは`_task_handle == nullptr`時の空処理と区別できないため、running/enabledも監視する。条件を保証できない版へ更新する場合は、完了通知を持つadapterまたはPCMを内部バッファへコピーするI2S sinkへ切り替える。

停止・失敗・再初期化では「何ms経過したから安全」と解放しない。M5のタスク停止・参照解放が完了するまで送信済みslotを隔離する。停止要求もsinkの所有タスクで実行し、失敗時は無音へ遷移して状態をログに残す。最後の1〜2枚は次の送信がなければ保持し続けてよい。

## 有限の処理とキュー水位

生産ループには現在導入済みの「開始時に固定した最大ブロック数」を残し、合成時間上限も設ける。消費側も開始時のREADY数または最大ブロック数を固定し、ログ判定とyieldを必ず通る。スピーカー待機はCore0の音声タスクだけで行い、Core1を待たせない。

初期の15625Hz・512 samples/blockは維持して比較し、所有権解消後に256 samples/block（16.384ms）を評価する。最終水位は「ring待ち + sink current/next + DMA」の全体で定める。512 samplesを2枚積んだだけでも65.536msあり、通知・DMA・ゲスト遅延が加わるため、1ブロック32.768msをそのまま効果音遅延と呼ばない。

目標は定常出力待ち50〜100ms、入力から効果音までp95 150ms以下。これは設計値で、現行達成値ではない。最長の合成/描画/スケジュール停止を吸収する水位と、操作遅延を同時に測って選ぶ。underflowは無音補完数として、満杯はバックプレッシャーまたは破棄として別に記録する。現行`droppedBlocks`だけでは両者を判別できない。

# 4. 音源をゲスト時間に同期する

現行は出力リングの空きを埋めるため、最新OPMレジスタとADPCM FIFOを使って実時間の必要量を合成する。CPUが遅い間は、ゲストが次の音符・ドラムデータを渡す前に音源だけが進む。そのため音程が一定でも音符の長さ・エンベロープ・ADPCM供給が異なる時間基準になる。短いキーオン/オフが同じCPU slice内にあると、中間音を合成せず最終レジスタだけ見る可能性もある。[^capture-tree]

最終設計はゲスト10MHzを基準に64bitのaudio clockを設ける。現在の15625Hzなら **640 guest cycles = 1 sample**。汎用化する場合は剰余を保持する整数位相累積を使い、毎ブロックの丸めで時刻を失わない。

```text
sample_target = floor(guest_cycles × sample_rate / guest_clock)
audioSyncTo(guest_cycles): audio_cursorからsample_targetまで、現在の音源状態で合成
```

`audioSyncTo(t)`はOPM data、ADPCM command/data、音声に影響するclock設定を書き換える直前に呼ぶ。ADPCM status等の時間依存readの前、CPU slice終了時にも追いつかせる。その後でレジスタを書き換えれば、同じslice内の短い音も時間順に残る。静音時はゼロ生成/時刻進行をまとめて省コスト化する。

時刻`t`は実際のCPU進行を反映させる。event-drivenの未反映debtとJITブロック内経過を含め、MMIOへ到達した命令境界で取得する。JITがMMIOをまたいでまとめ実行する経路はbarrierを設ける。最初の精度契約はエミュレータの命令境界精度とし、物理バスサイクル単位のYM2151再現を主張しない。

合成結果は端数を持つPCM accumulatorへ追記し、満ブロックでringへ公開する。再生水位だけを理由に未来のゲスト時刻まで合成しない。ring満杯でも音源内部の位相・FIFO時間を勝手に止めない。生成PCMを保持できない場合の破棄を明示し、通常の実時間運転ではゲスト実行をpacingして発生を防ぐ。

音量0/ミュートは出力の設定であり、ゲスト音源の時刻進行停止と同義にしない。ミュート中もFIFO・status・音源状態を進める。性能診断用の「合成処理そのものを外す」モードは、意味が違う診断条件として記録する。

## 実時間に届かない場合

高速化後の標準はゲスト等速、音声サンプル等速、LCDだけ負荷に応じて省略する。計算力が足りない場合、短期的な揺らぎは先読み水位で吸収し、尽きた分は無音補完・短いfadeで段差を抑え、その区間を計測する。バッファを増やして恒常的な速度不足を解消したとは扱わない。

継続的に10MHz未満の場合は「速度不足」の状態を明示し、安定性合格と実時間合格を分ける。スローモーションで連続した音を優先する任意モードは可能だが、単純リサンプルではテンポと音程が一緒に変わる。音程を保つタイムストレッチは追加CPUと遅延が必要な別設計であり、初期の改善範囲には入れない。現行の空き追従合成を正確な同期方式として残さない。

Core0で合成する発展案を採るなら、サイクル時刻付きの不変音源イベント列と独立した音源状態を渡す必要がある。ADPCM status/FIFOのゲスト側モデルとの整合も必要なので、単に`renderAudio(g_machine)`を別タスクへ移す案とは別物。計測でCore1の音合成が支配的だと分かるまで着手しない。

# 5. 音質の判定

非ゼロ波形だけでは、音符・テンポ・連続性・clipを保証しない。以下を同じ音源イベント列でホストPCMと実機出力経路へ流す。

1. 無音→単音→キーオフ→無音。周波数、エンベロープ、ブロック境界の不連続、DC、clipを検査する。
2. 1 slice内の短いキーオン/オフ、ブロック境界をまたぐ音程変更。分割サイズが違ってもPCMと音源状態が一致することを確認する。
3. ADPCM全バイトとニブル順、FIFOが一時的に空になる場合、再開・停止、FMとの重畳を確認する。ゲストデータ未供給と出力キューunderflowを別々に数える。
4. タイトルBGM、開始音、ジャンプ、被弾、アイテム、死亡、クリアを40/255で再生し、聴音または外部録音で途切れ・クリック・音割れを確認する。検証者と方法を残す。

FM+ADPCMの飽和加算でclipが増える場合は、合成前ゲインとheadroomを調整する。Speaker音量を下げるだけでは既にclipしたPCMは修復できない。ゲイン変更前後のピーク・clip数と聴音を比較する。原作NES音色の完全一致は別要件であり、現行OPM向けのKC対応表を、エミュレータ更新時に無検証で引き継がない。

# 段階ごとの成果物と合格条件

| 段階 | 実装対象 | 次へ進む判定 |
|---|---|---|
| P0 再現基準 | 実機ソース/ELF/入力/画像/ログの識別、正規化metrics、Core1でのモード適用 | 同条件3回で結果比較可能。ゲーム状態とゲスト時間が対応する |
| P1 音の安全性 | read lease、sink専用3slot、有限生産/消費、失敗/停止処理 | 任意スケジュールの偽非同期sinkで参照中上書きゼロ。ring wrap/満杯/停止・再開を含む。実機10分watchdog/resetゼロ |
| P2 実行と表示予算 | event-driven/JIT比較、描画実時間budget、公開前backpressure | 画面・状態・音イベント回帰なし。音ON/OFFを別条件で実効速度とp95遅延比較。時間予算に収まる表示fpsを選ぶ |
| P3 局所再合成 | tile世代、全書き込み入口の無効化、行/tile作業領域 | 全面参照rendererと画素完全一致。旧位置の消去、二重バッファ、公開失敗、scroll/zoom/paletteを含む。再合成費が実機で減る |
| P4 音の時間同期 | audio clock、MMIO境界sync、pacing、underflow補完 | slice/JIT分割に依存しないPCM・FIFO状態。音イベント順序一致。音声欠落と遅延を実測 |
| P5 統合判定 | 全ステージ・ボス・pause・再開、聴音/録音、30分連続動作 | watchdog/reset/参照中上書きゼロ。ゲーム全編実機で操作確認。別途、下記の実時間基準を判定 |

最終の実時間基準は、音ON・選定したLCD設定で、通常場面の各60秒区間についてゲスト時間/実時間が0.98〜1.02（pacing込み）、定常underflow/overflowゼロ、操作→効果音p95 150ms以下を目標とする。重い場面の最大遅延も併記し、平均値だけで合格にしない。初期の速度不足状態でも安全性の改善は独立して評価する。

テストの配置は、純粋なchannel/clock/dirtyロジックをホスト単体、全面合成との比較をホスト画像テスト、M5 adapterの待機・参照契約とSRAM/PSRAM/スケジュールを実機試験とする。ホストの高いfpsをCoreS3の性能根拠にしない。`core/`の計測へESP-IDF依存を入れず、platform側または注入した時刻取得器で計る。

実装は主にエミュレータ側`main/main.cpp`、`platform/audio.*`、`speaker_m5.h`、`frame_channel.*`、`display_lcd.*`、`core/machine.*`、bus/各video deviceを対象とする。このゲームリポジトリは再現入力、参照画像・音源イベント、設計・結果記録を持つ。実機系統と通常系統の統合は、既存最適化と未コミット変更を比較した上で最小単位に分ける。
