# 動機

実機の統計で 1 ブロック 2.04 命令 (blocks=67,291,085 / insns=137,239,578)。
[上流の実測](../../x68k-stackchan/docs/knowledge/event-driven-implementation.md)で
**ブロック 1 本の往復 D = 218.3 サイクル (ホストサイクルの 30.3%)** が測られている。
2 命令ぶんの利得しか出ないなら、被覆を広げるより区間を伸ばす方が効く。[^emu-knowledge]

被覆は 85.0% → 90.6% へ広げても速度がほとんど動かず、arena 容量も 3 通り振って
全部悪化した。[^prev-arena] **どちらも「区間の長さ」を変えない軸だった。**

# 測り方

`BlockEnd` の分布は実機でも上流でも**ゲーム中に一度も測られていなかった**
(`BlockSlot` が 40 バイト固定で `end` を持てず、runner は `endsWithBranch` の
2 値しか数えていない)。ホストの `x68k-run` に `--block-ends-from` を足し、
**1 命令ごとに、その PC がブロック先頭なら本物の `BlockPlanner::plan` を呼ぶ**
形で動的実行に沿って数えた。`PlanSource` は窓の中しか読まないので副作用は無い。

900M サイクル走らせ、**起動とタイトルを除く 500M 以降**を集計した
(全区間だと Human68k の起動が混ざって kBranch が 74.6% に薄まる)。

# 結果: 区間を切っているのは Bcc 終端

    計画 13,923,211 本 / 命令 36,963,941 / 平均 2.655 命令

| 終端 | 本数 | 割合 | 平均長 |
| --- | ---: | ---: | ---: |
| **kBranch** | 12,503,693 | **89.80%** | 2.59 |
| kUnknownLength | 612,771 | 4.40% | 2.58 |
| kCapacity | 387,250 | 2.78% | 6.00 |
| kUnsupported | 323,171 | 2.32% | 1.49 |
| kDynamicBranch | 87,058 | 0.63% | 2.28 |
| kMovemTooManyRegs | 4,750 | 0.03% | 1.59 |
| kPageBoundary | 4,518 | 0.03% | 1.57 |

**ページ境界も動的分岐 (RTS/JSR) も的ではない。** 合わせて 0.66% しかない。
これは Human68k 稼働中の内訳 (動的分岐 23.2%) とまったく違う。
ゲームは 1 フレームのループを回すので、サブルーチンの出入りが少ない。

## kBranch の内訳と帰趨

    BRA 52,533 / Bcc 12,426,579 / BSR 24,581
    後方(ループ) 6,187,509 / 前方 6,316,184
    Bcc の帰趨: 成立 6,639,635 (53.4%) / 不成立 5,782,724 (46.5%)

**kBranch の 99.4% が Bcc。** BRA と BSR は合わせて 0.6% しかない。
そして **その 46.5% は不成立**、つまり素通りして次の命令へ進む。

`plan()` は Bcc を必ず末尾に置く (I6)。不成立で素通りしたとき、
**ブロックは「次の命令から」もう 1 本組み直され、218 サイクルの往復を
1 回まるごと余計に払う。** 得ているのは分岐 1 本ぶんの区切りだけ。

# 中間 Bcc を許すと平均 2.655 → 4.33 命令

2 通りに数えて一致した。

| 数え方 | 平均命令/ブロック |
| --- | ---: |
| 現状 | **2.655** |
| 不成立 Bcc を新ブロックとして数えない | 4.447 |
| **不成立側へ本物の planner を継いで kMaxOps まで積む** | **4.332** |

後者の長さ分布は `4:35.6% 6:45.1%` で、**45.1% が kMaxOps = 6 の天井に当たる**。
つまりこの変更を入れると、**今度は kMaxOps が律速になる** (現状は 2.78% しか
当たっていない)。段 E の掃引 (4→6 で +2.7%、6 以上は飽和) は
**中間 Bcc が無い前提での飽和**なので、この変更後は測り直しが要る。

D は Human68k で測った値で、ゲームでは測っていない。**着手前にゲームで

# direct chaining とは別物

上流の段 D-1 (ランナー内ディスパッチループ) は実測 -2.47% で撤退した。
理由は **呼び出しの 69% が 1 本も走らずに戻り、回収する往復を持たないのに
ループの費用だけを払った**こと。

中間 Bcc はそれと構造が違う:

- チェーンは**呼び出しをまたぐ**ので「出番が来るか」に懸かる。
  段 D-1 はそこで外した
- 中間 Bcc は**1 本のブロックの内側**。翻訳できた時点で往復は確実に消え、
  「出番」という条件が存在しない
- 生成コードへ何も焼かないので、direct chaining が棄却された理由
  (逆リンク・非アトミックな patch・pull 型が壊れる) がどれも当たらない

エミッタ側の機構も既にある。`emitBranchExit` は条件を評価して
**成立側の出口と不成立側の出口を既に 2 つ吐いている**。中間 Bcc は
「不成立側の出口を吐く代わりに、次の命令の発行を続ける」だけ。

# kUnknownLength は 100% がシフト命令 ($E 群)

終端の原因になった命令語を上位 4bit で数えたら、
**kUnknownLength 612,771 件の 100% が $E**。他の群は 1 件も無い。

`m68k_length.h` の `instructionLength` は $E を `default:` で
`kUnknownLength` に落としている。**レジスタ形のシフト/ローテート
(bits 7-6 != 11) は拡張ワードを持たず、常に 2 バイト**なので、
判別 1 本で確実に取れる (3,072 通り)。メモリ形 (bits 7-6 == 11) は EA を取る。

長さが分かるだけではブロックに積めない (`planOne` の許可リストも要る) が、
**長さだけ分かれば「その手前で切る」必要が消える**わけではない —— 積めない
命令は `kUnsupported` で切れる。ただし
[前の記録](jit-hot-rejects.md)でシフト/ローテートは実行 1,529,295 回
(全体の 1.89%) の JIT 不可命令として 2 位に挙がっており、
**長さと許可リストを同時に足せば 4.40% の終端がまるごと消える**。

`test/test_scheduler.cpp:1561` に **65,536 通りの全数検証**があり、
実際に 1 命令実行して PC の進み量と突き合わせている。$E を足せば
自動で検証される。

# やっていないこと

- ゲームでの D の実測 (Human68k の 218.3 を流用している)
- 中間 Bcc を入れた後の kMaxOps 掃引
- 生成コードのバイト数が増えることによる arena への逆風の実測。
  段 E では「1 本が長くなるぶん 1 本が覆う命令数も増える」ので
  バイト/命令はほぼ不変だったが、中間 Bcc は**条件評価と出口を
  ブロックの内側に増やす**ので同じとは限らない
- `kMaxVerifyWords = 8`。段 F/G で「kMaxOps を 4→6 にしたら 2 本が
  控えを持てなくなった」を踏んでいる。平均 4.33 命令 (最大 6) は
  最大 12 語を超えるので、**この上限に当たる本数が増える**
