# 現在の差分・検証の境界

- 対象は現行x68k-stackchanのHuman68k実行環境。物理X68000およびCoreS3のLCD・スピーカーでは未検証。
- ゲームのフレーム定数はNESから保持し、エミュレータの垂直同期55.45Hzを使う。処理が1VBlankに収まる場合でも実時間はNESより約8%長い。ロード時の描画時間や実機のフレーム落ちまで同一とは保証していない。
- APUの波形そのものをエミュレートする移植ではない。FM音色・スイープ・ビブラート・ノイズは近似で、ドラムとハイハットはADPCM 1声の優先再生。NESとの音色・同時発音の完全一致は対象外。
- 現行エミュレータのOPMはKC=0を約8.1758Hz、音名を`note - (note >> 2)`として扱う。音程表はこの実装へ合わせた。物理YM2151への対応では音程表の見直しとBUSY待ちが必要。
- ADPCMは現行エミュレータの256byte FIFOへ毎フレーム最大141byteを送る。実チップへの対応にはDMA等の一定速度の転送が必要。この方式だけで物理MSM6258が動くとは主張しない。
- 原作のOPTIONは機能未実装のため、移植版も選択表示のみ。エンディングは原作字形と文面を使い、読みやすい白で表示する。

# 再発防止: 実際に遭遇した不具合

- `-m68000`だけでは十分ではなかった。GCCのstore-mergingが構造体の奇数オフセットに隣接するbyteをwordへまとめ、アドレス例外になった（game_init、`movew #165,%a2@(29)`）。`-mstrict-align -fno-store-merging`を追加して実バイナリの起動で再確認。
- 32bitの`% 6`が配布libgccの除算ヘルパーを取り込み、その中の68020用`bsr.l`で初代68000が落ちた。SFXの切り替えを比較と減算に変え、ビルド時に除算・剰余ヘルパーの混入を検出する。
- 原作HUDを入れた後、デバッグ行が主人公アイコン等と重なりE2Eの数字復元が壊れた。テスト専用のデバッグ行を0行目へ分離し、HUDは状態が変わったときだけ描く。
- `.byte`がラベルと同じ行にある`go_pat`を読み落としていた。パーサーを修正し、原作の8音との完全一致を回帰テストにした。
- 通常版のタイトル撮影でHuman68kのカーソルがTVRAMに再描画されるのを確認し、起動時にIOCSのカーソル停止を呼んで解消した。従来の「8色以上」検査はカーソルの余計な1色を数えていた。除去後の390Mサイクルの正しいタイトルは明色16939画素・7色で、ロゴ色循環の相を考慮した条件へ訂正した。
- `just screenshot-title`は通常版GAME.Xを390Mサイクルまで実行して描画器から256×240のゲーム領域を直接取得し、PNGへ形式変換する。撮影後の絵の描き替えは行わない。

## 追記: LCDフレーム取得と小音量での起動確認

実機と同じ `e4356d6` の隔離worktree
`/private/tmp/x68k-device-capture` に、LCDへ送信した320×240 RGB565フレームを
`?` でUSBシリアル出力する機能と `just capture-lcd` を追加した。
`FrameChannel::take()` と `done()` の間で取得し、送信中の書き換えを防ぐ。
画像は実機のフレームからPPM/PNGへ変換したもので、ホストエミュレータの再描画ではない。

`build-x68k/cores3-title.png` をエージェントが目視し、タイトルイラストと
START / CONTINUE / OPTIONが表示されていることを確認した。
LCDパネル自体をカメラ撮影したわけではない。

音声生産ループは消費側が同時に空きを作ると終了条件を満たさないため、
開始時の空き枚数を固定上限にした。ユーザー指定でM5.Speakerの音量は40/255。
小音量設定を含むアプリ607584 bytesを0x10000へ書き込み、hash照合成功。
旧アプリのバックアップは `/tmp/x68k-firmware-before-capture.bin`。
音源ONのゲーム起動後約30秒のログで非ゼロ振幅と出力ブロック数を確認し、
その区間にwatchdog警告は出なかった。人の耳による音質評価や長時間安定性は未検証。

USB再接続時に再起動するため、取得スクリプトは20秒待ってGAMEを入力し、
さらに40秒待ってタイトルを取得する。変更は隔離worktreeに未コミットで残している。
