# きっかけ

[JIT被覆を上げたら遅くなった](jit-hot-rejects.md)の原因として、
実機の統計に `full=107,663,755` (ブロック入口失敗の48.4%) が出ていた。
arena が満杯で翻訳できない状態が支配的に見えたので、容量側を振った。

# 3通り試して全部悪化した

いずれも同じ操作台本 (右移動+ジャンプを周期送出) で、
ゲーム中85サンプルの平均。

| 条件 | CPU実効 | 音声不足 | fps |
| --- | ---: | ---: | ---: |
| 基準 (スロット1024 / コード32KiB / 閾値1M) | **4,601 kHz** | 54.0% | 7.73 |
| reset閾値 1,000,000 → 20,000 | 4,531 kHz | 54.7% | 7.74 |
| スロット512 / コード48KiB | 4,417 kHz | 55.9% | 7.83 |

**どれも基準より遅い。**

## reset閾値を下げても効かない

`full` は 107,663,755 → 52,395,295 と半減し、`reset` は 107 → 2,619 へ
24倍になった。満杯の回数自体は確かに減っている。それでも速度は
4,601 → 4,531 kHz と微減した。

捨てる回数が増えた分、常駐ブロックの再翻訳費用が相殺している。
閾値を上げても下げても改善しないので、これは調整点ではない。

## arena を広げても効かない

スロットを1024→512に減らしてコードを32→48KiBへ振り替えた。
確保は成功し (`JIT スロット 512 個 (20480 バイト) を確保しました`)、
JITも有効なまま (`jit_active=1` が102/102)。それでも 4,417 kHz と最も遅い。

`full` はむしろ 119,191,158 へ増えた。コード領域を広げたのに満杯が増える
のは、スロットを減らしたことで索引の衝突が増え、同じ番地を何度も
翻訳し直しているためと考えられる (未検証)。

# 【追記】真因は arena でも JIT でもなく OPM レートだった

その後 A/B を 1 変数ずつやり直したところ、

| 条件 | CPU実効 |
| --- | ---: |
| OPM 15625Hz | **5,208 kHz** |
| OPM 62500Hz | 4,601 kHz |

**音源の合成レートを4倍にしたことが 11.7% を食っていた。**
JIT被覆拡大は ON の方が速く (4,601 対 4,470)、arena 容量の3実験も
すべてこのレート変更後に測っていたため、全部同じ底上げされた土俵で
比べていた。下の「arena は律速ではない」という結論自体は変わらないが、
比較の基準にしていた 4,601 kHz はレート変更で既に落ちた後の値である。

# 解釈: arena は律速ではない

当初「満杯48.4%」を律速と読んだが、容量をどちらへ振っても改善しないので
その読みは誤りである。`full` の回数は結果であって原因ではない。

より整合する説明は、[前の記録](jit-hot-rejects.md)で書いたとおり
**被覆を広げたことで1ブロックが太り、翻訳の費用そのものが増えた**こと。
arena を広げても、太ったブロックがその分場所を食うので相殺される。

# やっていないこと

- **eviction (個別ブロックの追い出し) は実装していない。** arena は
  バンプアロケータで、個別解放には確保器そのものの作り替えが要る。
  ただし上の3実験から、それをやっても効く保証は無い。
  「満杯が減れば速くなる」が閾値実験で否定されているためである。
- 被覆拡大 (ANDI/CMPA) を戻したときに 4,987 kHz へ回復するかは未測定。
  これを測れば「太ったブロックが原因」を直接確かめられる。次はここ。

# 教訓

統計の最大値がそのまま律速とは限らない。`full=48.4%` は目立つが、
それを減らす方向 (閾値↓) と、溢れにくくする方向 (容量↑) の
**両方を試して両方悪化した**。片方だけ試して「効かなかった」と
結論していたら、原因を取り違えたまま次へ進んでいた。
