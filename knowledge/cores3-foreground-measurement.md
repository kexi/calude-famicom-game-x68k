# 計測条件

前景16bit版(コミット df99e9d)を書き込んだCoreS3を、シリアル接続1本で
約520秒動かした。内訳は起動待ち45秒、`game`打鍵後のロードとタイトル45秒、
以降430秒がゲーム中。ゲーム中は右移動とジャンプを周期的に送り、
放置死ではない実プレイに近づけた。5秒ごとの定期ログ103サンプルを集計した。[^log]

**JITは全区間で無効だった** (`[runtime] jit_active=0`、103/103サンプル)。
`event_driven=0`でもある。以下はJIT無しの基準値であり、
JIT有効時の値ではない。過去のJIT有効計測と直接比較してはいけない。

ゲーム中は実機10MHz目標に対して約39%。タイトル画面より約23%遅い。

# 音声

`[audio-continuity]`の差分。`missing_frames`は「ゲストが供給できず
無音で埋めたブロック」の累積なので、不足率は missing/(source+missing)。[^playback]

| 区間 | source | missing | 不足率 |
| --- | ---: | ---: | ---: |
| ロード〜タイトル | 361,984 | 368,128 | 50.4% |
| ゲーム全体 | 2,613,248 | 4,052,992 | **60.8%** |
| ゲーム前半 | 993,280 | 1,451,008 | 59.4% |
| ゲーム中盤 | 846,336 | 1,486,848 | 63.7% |
| ゲーム後半 | 762,880 | 1,094,144 | 58.9% |

一方で再生側は安定している。`blocks_per_sec`は平均30.52
(理論値 15625Hz/512 = 30.5)、`dropped=0`、`muted_frames=0`、
`paused_frames=0 failed_frames=0 restarts=0`。

つまり **LCDへの供給経路は詰まっておらず、ゲスト側がPCMを作れていない**。
不足の原因は再生でもDMAでもなく、68000の実行速度である。
時間経過で悪化する傾向は見られない(前半59.4%→後半58.9%)。

# 不足率はCPU速度と恒等的に一致する

PCMはゲスト時間に固定で結び付いている。`GuestAudioProducer`は
`kCyclesPerSample = 640`、`samples = cycles / 640`で合成するので、
15625Hzを満たすには **ゲストが10MHzちょうどで回る必要がある**
(640 × 15625 = 10,000,000)。[^playback]

したがって供給率はCPU実効速度の10MHzに対する比そのものになる。

    実測 3.92MHz / 10MHz = 39.2%  →  不足 60.8%
    ログの実測不足                      60.8%

5秒窓420個それぞれで「その窓の実効kHzの10MHz比」と「その窓の供給率」を
突き合わせたところ、差の平均は **-0.0ポイント** だった。
偶然の一致ではなく恒等関係である。

`dropped=0`が509サンプル全てで成立していることも整合する。リングが
溢れないのは、ゲストが実時間より先へ出ることが一度も無かったからである。

**この結果は「音声側に直すべきバグは無い」ことを意味する。** 出力段・
DMA・キュー・pacingをどう改善しても不足率は1ポイントも動かない。
不足を減らす方法はCPU実効速度を上げることだけで、10MHzに達した時点で
不足は自動的に0になる。音声不足はCPU速度の別表現にすぎない。

これは過去に音声側を疑って積み上げた一連の調査
([lifecycle](cores3-audio-lifecycle.md)・[同期再生](cores3-synchronized-playback.md)・
[ゲスト時計](cores3-guest-audio-clock.md)等)に対する結論でもある。
それらで入れた仕組み自体は正しく動いており(drop/mute/restartがすべて0)、
残った不足はもうその層の問題ではない。

# 評価

- 音声不足60.8%は[MOVE命令時間修正](cores3-move-timing.md)時点の56.8%と
  同程度で、前景16bit化によって目立って悪化はしていない。ただしJITの有無が
  揃っていないため、厳密な比較にはならない。
- 描画占有21.4%に対しCPU占有74.5%。描画を削るより68000の実行を速くする方が
  効く配分である。JIT無効が最大の要因と考えられる。
- 7.3fpsは遊べる速度ではない。

# JIT有効での再計測 (2026-09-06)

`jit_active=0` の理由が分かった。`g_jitToggleRequests` が 0 始まり、
`g_eventDrivenEnabled` が false 始まりで、**JITもイベント駆動も既定でOFF**
だった。シリアルに `J` を送ると両方ONになる。JITはイベント駆動の経路にしか
無いので、この2つは連動している。

JITを有効にして同じ条件で測り直した。

| 指標 | JIT無効 | JIT有効 | 既定ON化後 |
| --- | ---: | ---: | ---: |
| CPU実効 (ゲーム中平均) | 3,920 kHz | 5,044 kHz | 4,987 kHz |
| 音声不足 | 60.8% | 49.5% | 50.1% |
| 予測値 (1 - MHz/10) | 60.8% | 49.6% | 50.1% |
| 描画 fps | 7.30 | 7.81 | 7.77 |

**恒等関係は3回とも成立した。** 予測と実測の差は最大0.1ポイントである。
JITでCPUが上がった分だけ、そのまま音声不足が減った。これで
「不足はCPU速度の別表現であり、音声側に直すべきバグは無い」という
前節の結論が、条件を変えた実測でも裏付けられた。

10MHzに到達すれば不足は0になる。逆に言えば、CPUが約5MHzのままでは
何をしても不足は約50%から動かない。

# 既定の変更 (2026-09-06)

ユーザーの指示で、実機ファームの既定を2つ変えた。

- **JITを既定ON**。`g_jitToggleRequests` を 1 で始め、最初のスライスで
  1回ぶんの切り替えを消費させる。置き場の確保と失敗時の退避は既存の
  ループ内にあるので、初期化の順序を二重に持たない。
- **主旋律ブーストを既定ON**。`g_melodyBoostEnabled` を true にする。
  OFFだと主旋律が他声部に埋もれて聞こえないという実機の聴感報告があり、
  この補正込み (gain 8倍・ピークだけ17000で圧縮) でバランスを決めてある。
  他のソフトを鳴らすときは `-` で切れる。

書き込み後の実機で `[melody-gain] channel=1 gain_q8=2048 peak_limit=17000` を
起動時に確認し、`jit_active=1` が102/102サンプルで成立した。

これらの変更は `/private/tmp/x68k-device-capture` の作業ツリーにある。
ghq の checkout とは `main.cpp` が大きく分岐しており (2,843行 対 3,324行、
主旋律ブースト機能自体が ghq 側に無い)、そのままでは移植できない。
作業ツリー側の変更が main へ入るときに一緒に持っていく必要がある。

# 条件別の比較 (2026-09-06)

同じ操作台本 (右移動とジャンプを周期的に送る) で条件を変えて測った。
ジャンプを混ぜるのは、障害物で止まるとスクロールが進まず、
「動いている間の費用」を測れなくなるため。

| 条件 | CPU実効 | 音声不足 | 予測 | fps | 描画/frame |
| --- | ---: | ---: | ---: | ---: | ---: |
| 16bit・JIT無効 | 3,920 kHz | 60.8% | 60.8% | 7.30 | 28.4ms |
| 16bit・既定ON | 4,987 kHz | 50.1% | 50.1% | 7.77 | 27.7ms |
| 4bit・既定ON | 5,459 kHz | 45.4% | 45.4% | 7.86 | 34.1ms |
| **16bit・背景OFF** | **5,715 kHz** | **42.9%** | 42.8% | 7.78 | **22.2ms** |

**恒等関係は6条件すべてで成立した。** 予測と実測の差は最大0.1ポイント。

読み取れること。

- **遠景の合成が最も重い**。背景OFFで描画が27.7→22.2ms (-20%)、
  CPUが4,987→5,715kHz (+15%)。前景16bit化そのものより、
  毎フレーム320×240の遠景を読み出して合成する費用が支配的である。
- 4bitは16bitより速い(5,459 vs 4,987kHz)が、描画時間は逆に長い
  (34.1 vs 27.7ms)。4bitはハードのBG/スプライトを使うぶんCPUは軽いが、
  LCDへ送る合成はエミュレータ側の別経路を通るためと考えられる。
- fpsはどの条件でも7.8前後で頭打ち。描画時間が20〜34msと幅があるのに
  fpsが動かないので、fpsを縛っているのは描画ではない。

背景OFFは計測専用のビルド (`-DCALUDE_BENCH_NO_BACKGROUND`) で、
遠景の読み出しを黒で置き換えたもの。配布物には入れていない。
`just build 0 "-DCALUDE_BENCH_NO_BACKGROUND"` で再現できる。

# 主旋律ブーストの定量確認 (2026-09-06)

「メロディーが聞こえない」という実機の報告を、聴感ではなく合成波形で確かめた。
`just test-audio-balance` でタイトル曲20秒を実際の音色で合成し、
主旋律ゲインを変えて比較する。

| lead_gain_q8 | mix rms | 他声部 rms | 主旋律 rms(推定) | 他声部比 |
| ---: | ---: | ---: | ---: | ---: |
| 256 (OFF) | 2,869 | 2,559 | 1,297 | **-5.9 dB** |
| 2048 (ON) | 9,577 | 2,559 | 9,229 | **+11.1 dB** |

主旋律rmsは`sqrt(mix^2 - other^2)`による推定(無相関近似)。

**OFFでは主旋律が他声部より5.9dB小さい。** 報告どおり埋もれる。
ONで+11.1dBとなり、17.0dBの差がつく。

飽和は起きていない。効果音を含む36シナリオ全体で
`mix_raw peak=30363` (16bit上限32767に対し余裕7%)、
`clipped=0 fm_clipped=0 fm_rail_samples=0`。
ピーク圧縮(peak_limit=17000)が効いている。

これで既定ONの妥当性は数値で裏付けられた。実機での聴感確認は残るが、
「聞こえない」の原因が既定OFFだったことは確定した。

パート別に書き出したWAVでも同じ結論になる (既定ON時)。

| パート | rms | peak |
| --- | ---: | ---: |
| lead (主旋律) | 9,085 | 16,908 |
| bass | 1,269 | 2,408 |
| harmony | 151 | 468 |

主旋律が他パートを明確に上回っている。
`just test-audio-balance 20 <prefix> 0 <gain> <limit>` で
mix/lead/harmony/bass/fm/adpcm/sfx のWAVを書き出せるので、
既定を変える前後の聴き比べはホストだけで再現できる。

# 未計測・次にやること

1. 実機スピーカーでの聴感確認。数値上は+11.1dBで埋もれないはずだが、
   スピーカー特性込みの印象は測っていない。ホスト合成のWAVは
   ユーザーへ送付済みで、そちらでの判断は可能。
2. 遠景合成の最適化。背景OFFの数字が上限の目安になる。

   原因は特定できている。`hc_set_scroll` はスクロールのたびに、
   terrainを含む行すべてを「旧位置と新位置の和」でdirtyにする。
   地形は画面幅いっぱいに続くので、**スクロール中はほぼ全行が全幅dirty**
   になり、320×240=76,800 wordぶんの遠景を毎フレーム読んで合成する。

   一方 GVRAM へ実際に書くのは p95 15,377 word (20.0%) しかない。
   影バッファの同値抑止が効いているためである。
   **つまり合成のために読む量が、書く量の約5倍ある。**
   背景OFFで描画が27.7→22.2ms (-5.5ms) 減ったのは、この読み出し分に当たる。

   **ただし「dirty範囲を狭める」では解決しない。** スクロールで地形が2px動くと、
   地形が乗る画素の最終色は実際に変わる。地形は画面幅いっぱいに続くので、
   ほぼ全幅で色が変わるのは正しい。影バッファが弾いている80%は、
   地形の無い上空など「遠景しか無いので色が変わらない」画素である。

   つまり無駄なのは範囲ではなく、**遠景しか無い画素についても
   毎フレーム遠景を読み直して合成し、影バッファで捨てている**こと。
   **(a) は試して失敗した。** 「その行に地形・スプライト・文字が1つも
   乗らないなら合成ごと飛ばす」を実装したところ、renderer の225frames
   全画素試験が落ちた。理由は、行がdirtyになるのは「いま何かが乗っている」
   ときだけではないこと。**前フレームまで乗っていたスプライトが抜けた行も
   dirtyになる**が、その時点では何も乗っていない。飛ばすと古い絵が
   残ったままになる。「乗っているか」ではなく「前フレームと同じ絵か」で
   判定しないと成立しない。

   残る打ち手:
   (b) 遠景と地形を合成した結果を行単位でキャッシュし、スクロール量が
       同じ間は再利用する。
   (c) 影バッファを行単位のハッシュ等で先に比較し、一致する行の合成を省く。
   いずれも未実装・未計測。背景OFFの5,715kHz / 22.2msが上限の目安になる。
3. ~~fpsが7.8で頭打ちになる理由~~ → 分かった。**68000の実行速度が律速**。
   背景OFF条件でも描画占有15.2%に対しCPU占有77.3%で、描画は律速ではない。
   1frame分のゲスト処理が終わらないと次のフレームを描けないため、
   fpsは実効MHzに従う。描画を0にしてもfpsは大きくは伸びない。

   これは音声不足がCPU速度と恒等的に一致することとも整合する。
   **速度・音声・fpsの3つとも、68000の実効MHzという単一の量で決まっている。**
   したがって描画側の最適化(遠景キャッシュ等)は、音声とfpsには効かない。
   効くのはCPU占有を下げる分だけで、上限は背景OFFの5,715kHz付近である。
4. 全ステージ・ボス・長時間。
2. 4bitモードとの同条件比較。今回は16bitのみで、前景16bit化の
   速度コストを分離できていない。
3. 全ステージ・ボス・長時間(数十分)。今回は430秒で1-1周辺のみ。
4. 音質の聴感確認。不足60.8%が実際どう聞こえるかは数値では分からない。
5. リング方式は実機未接続のまま。
